# Pixel Agent Office — 로컬 협업 앱 설계

작성일: 2026-09-25 · 상태: 기본 설계 승인 완료, 직급 페르소나 추가 요구 반영

## 1. 목표와 첫 버전 범위

사용자가 브라우저의 픽셀 사무실에서 자신의 컴퓨터에 설치된 Claude Code와 Codex에게 개발 작업을 맡긴다. 캐릭터를 선택해 실제 실행 중인 작업, 도구 호출, 변경 파일, 결과를 확인한다. 두 에이전트가 작업 결과를 주고받는 과정도 화면에 표시한다.

사용자가 선택한 방향은 **화면에서 직접 작업을 시작하고 협업을 관리하는 로컬 앱**이다. 아래의 한 프로젝트·한 팀 구성, 역할 배분, 화면 배치는 첫 버전을 작게 완성하기 위한 제안이다.

첫 버전의 완료 조건은 실제 Git 프로젝트에 대해 `작업 입력 → Codex 구현 → Claude 검토 → 필요시 Codex 수정 → 결과 확인`을 한 화면에서 끝내는 것이다. 두 CLI의 설치는 확인했으며 인증 상태와 실제 실행 연동은 구현 단계에서 검증한다.

포함 범위:

- 로컬 Git 프로젝트 선택 및 연결 상태 확인.
- Claude·Codex 캐릭터 각 1명으로 구성한 픽셀 사무실.
- 모델과 함께 설정하는 시니어·주니어·신입 직급 페르소나.
- Codex 단독, Claude 단독, 두 에이전트 협업 실행.
- 현재 작업, 스트리밍 출력, 도구 실행, 변경 파일, 작업 결과 표시.
- 실행 중단, 승인 요청 응답, 사용자 질문 응답.
- 실행 기록 저장 및 브라우저 새로고침 후 진행 상황 복원.

후속 범위: 원격 팀 접속, 로그인·결제, 맵 편집기, 다수 프로젝트 동시 실행, 터미널에서 독립적으로 시작한 세션 자동 수집, 임의 수의 에이전트 자동 생성.

## 2. 접근 방식 비교와 선택

| 방식 | 이점 | 제약 |
|---|---|---|
| **로컬 웹 앱 + 로컬 실행 서버 — 선택** | 설치된 Claude·Codex와 로컬 프로젝트를 연결하고 브라우저에서 관찰 가능 | 실행 서버를 켜 두어야 함 |
| 데스크톱 앱 | 파일 선택과 프로세스 관리 통합이 자연스러움 | 패키징·배포 작업이 초기 범위를 늘림 |
| 클라우드 웹 서비스 | 여러 컴퓨터에서 접속 가능 | 별도 실행 환경·인증·프로젝트 동기화 필요 |

첫 버전은 로컬 웹 앱으로 구현한다. 에이전트 연결 모듈을 UI와 분리해 이후 데스크톱 앱으로 감싸거나 실행 서버를 확장할 수 있게 한다.

## 3. 사용자 흐름

1. 앱을 실행해 브라우저에서 연다. 서버는 루프백 주소에만 바인딩한다.
2. 프로젝트의 절대 경로를 입력한다. Git 저장소 여부와 두 실행 도구의 연결 가능 여부를 점검한다. 잘못된 경로와 연결 실패는 화면에서 원인과 함께 표시한다.
3. 각 에이전트의 모델과 직급을 설정하고 작업 설명·실행 방식(협업 / Codex 단독 / Claude 단독)을 선택한다. 협업 기본 역할은 Codex 구현, Claude 검토이며 역할을 바꿀 수 있다. 모델을 지정하지 않으면 공급자 기본 설정을 사용한다.
4. 실행하면 전용 브랜치와 Git worktree를 생성한다. 기존 프로젝트의 커밋되지 않은 변경은 자동으로 옮기거나 덮어쓰지 않는다. 시작 기준 커밋과 별도 작업 폴더 사용 사실을 화면에 표시한다.
5. 에이전트가 작업하면 캐릭터와 상태가 실시간으로 바뀐다. 캐릭터를 누르면 해당 에이전트의 활동 패널이 열린다.
6. 승인이 필요하면 요청 내용을 확인하고 승인·거절한다. 사용자 질문이 있으면 같은 패널에서 답한다.
7. 협업 실행에서는 구현 결과와 변경 파일을 검토자에게 전달한다. 지적 사항이 있으면 구현자에게 수정 작업을 전달한다.
8. 완료 화면에서 결과 요약, 변경 파일과 diff, 실행·테스트 결과, 작업 브랜치와 폴더를 확인한다. 원본 브랜치 병합이나 원격 푸시는 자동으로 수행하지 않는다.

## 4. 화면과 시각 동작

기본 시각 방향은 ZEP에서 영감을 받은 탑다운 2D 픽셀 사무실이다. 자체 제작한 단순한 타일·캐릭터를 사용한다. UI 문구는 한국어로 제공한다.

```text
┌ 프로젝트 · 연결 상태 ───────────── 실행 상태 · 중단 ┐
│                                                   │
│  픽셀 사무실                  │ 에이전트 상세       │
│                               │ 이름 / 역할 / 상태  │
│  Claude 책상    Codex 책상     │ 현재 작업           │
│                               │ 활동 / 변경 파일    │
│  자료 공간      검토 테이블    │ 승인 / 질문 / 결과  │
│                                                   │
├ 작업 입력 · 실행 방식 · 시작 ──────────────────────┤
│ 협업 타임라인: 구현 → 검토 → 수정 → 완료            │
└───────────────────────────────────────────────────┘
```

| 관측한 상태 | 화면 표현 |
|---|---|
| 실행 전 또는 작업 없음 | 책상에서 대기, 대기 상태 배지 |
| 응답 생성 중 | 책상에서 작업, 응답 중 배지 |
| 파일 탐색·읽기 | 자료 공간 이동, 읽는 파일 또는 도구 이름 표시 |
| 파일 수정 | 책상에서 타이핑, 수정 중 배지 |
| 명령·테스트 실행 | 터미널 표시, 실행 중인 명령 표시 |
| 검토 작업 시작 | 검토 테이블 이동, 검토 중 배지 |
| 다른 에이전트에게 인계 | 인계 말풍선 및 타임라인 이벤트 |
| 승인·답변 대기 | 손들기 표시와 응답 필요 배지 |
| 완료·실패·중단 | 서로 구분되는 상태 배지와 결과 링크 |

에이전트의 내부 사고를 추정해 말풍선을 만들지 않는다. 명확히 분류할 수 없는 도구 실행은 '작업 중'으로 표시한다. 테스트 통과는 실제 명령 결과로 확인된 경우에만 표시한다. 메시지가 없다는 이유만으로 실패나 완료로 간주하지 않는다.

픽셀 사무실과 동일한 정보를 텍스트 에이전트 목록으로도 제공한다. 키보드로 에이전트를 선택할 수 있고, 움직임 감소 설정에서는 이동 애니메이션을 줄인다. 작은 화면에서는 상세 패널을 하단 또는 별도 탭으로 전환한다.

### 직급 페르소나와 모델 배치

사용자 추가 요구: 모델 성능에 맞춰 시니어·주니어·신입처럼 연차를 부여하고, 에이전트의 역할과 행동에서 차이가 드러나게 한다.

| 직급 | 업무 수행 지침 | 보고·협업 방식 |
|---|---|---|
| 시니어 | 요구사항의 모호함, 구조적 영향, 예외와 회귀 위험을 확인 | 판단 근거와 선택지를 제시하고 검토 결과에 책임 범위를 명시 |
| 주니어 | 합의된 범위의 구현과 테스트에 집중, 큰 구조 변경 전 질문 | 변경 내용·검증 결과·막힌 점을 구체적으로 보고 |
| 신입 | 명확하고 작은 단위의 수정·문서·테스트 작업 수행 | 범위를 벗어나거나 판단이 어려우면 질문하고 검토가 필요한 부분을 표시 |

공급자, 실제 모델, 직급, 현재 업무는 별도 값이다. 예를 들어 캐릭터에는 `Claude · 시니어 · 검토 중`, 상세 패널에는 선택 모델과 페르소나 지침을 표시한다. 직급이 시니어여도 구현 업무를 맡길 수 있고, 사용자 선택에 따라 같은 모델을 다른 직급으로 설정할 수 있다.

직급은 실제 경력이나 객관적 성능 점수를 뜻하지 않는 작업 페르소나다. 브랜드나 모델 이름만으로 성능 순위를 단정하거나 자동 승진시키지 않는다. 사용자가 모델 성능·비용·작업 특성을 판단해 직급을 배치한다. 자동 성능 평가와 벤치마크에 따른 배치는 후속 범위로 둔다.

첫 실행의 제안 프리셋은 **시니어 검토자 + 주니어 구현자**다. 기존 두 캐릭터에 적용하며 직급별 캐릭터를 추가 생성하지 않는다. 공급자별 우열을 뜻하지 않으며 구현·검토 역할과 함께 바꿀 수 있다. 신입을 선택할 때는 작은 작업을 맡기고 협업 모드의 검토를 권하는 짧은 안내를 표시한다.

직급에 따라 역할 프롬프트와 작업 범위·보고 형식을 조정한다. 파일·명령 권한, 사용자 승인 정책, 최대 수정 횟수는 직급과 별개로 유지한다. 페르소나는 행동 지침이며 모델이 반드시 준수한다는 보장은 하지 않는다. 실행 시작 시 모델·직급·지침 버전을 기록하고 진행 중에는 변경하지 않는다.

## 5. 구성과 데이터 흐름

프런트엔드는 React + TypeScript와 Canvas 2D를 사용한다. 폼·로그·diff는 DOM으로, 사무실 타일과 캐릭터는 Canvas로 렌더링한다. 로컬 서버는 Node.js + TypeScript를 사용한다. HTTP로 설정·기록을 조회하고 WebSocket으로 실행 이벤트와 사용자 응답을 전달한다. 실행 기록은 로컬 SQLite에 저장한다.

```text
브라우저: 사무실 / 작업 입력 / 상세 패널
                    ↕ HTTP + WebSocket
로컬 서버: 실행 관리 / 협업 제어 / 이벤트 저장
                 ↙                      ↘
       Codex 어댑터                 Claude 어댑터
       App Server                   Agent SDK
                 ↘                      ↙
                실행별 Git worktree
```

각 모듈의 책임:

- **프로젝트 관리:** 경로 검증, 기준 커밋 확인, 작업 브랜치·worktree 생성과 목록 관리.
- **에이전트 어댑터:** 세션 시작, 입력 전달, 중단, 승인·질문 응답, 공급자별 이벤트 변환.
- **협업 제어:** 작업 단계, 구현·검토 역할, 인계 데이터, 수정 횟수 관리.
- **이벤트 저장:** 실행 상태와 이벤트를 기록하고 구독자에게 순서대로 전달.
- **사무실 UI:** 서버 이벤트를 캐릭터 동작과 읽기 쉬운 상태로 표현.

Codex는 App Server의 세션·턴·도구 이벤트와 승인 프로토콜을 사용한다. Claude는 Agent SDK의 스트리밍 메시지와 권한 처리 기능을 사용한다. 모델 이름을 코드에 고정하지 않고 미지정 시 공급자 기본 설정을 따른다. 모델 선택은 공급자가 조회 기능을 제공하면 목록을 사용하고, 그렇지 않으면 모델 식별자 입력과 기본값 선택을 제공한다. 접근 불가능한 모델은 공급자 오류를 보여주고 몰래 다른 모델로 대체하지 않는다. 인증은 공식 도구가 지원하는 방식을 이용하며 기존 CLI 로그인이 SDK에서도 자동 재사용된다고 가정하지 않는다. 연결이 부족하면 해당 공급자에 필요한 설정을 표시한다.

브라우저에 자격 증명을 보내거나 셸 명령 문자열을 조립해 실행하지 않는다. 로컬 서버는 연결 토큰과 Origin 검증을 적용한다. 사용자가 지정한 프로젝트 경로는 서버에서 검증하며, 새 작업 폴더 생성에 필요한 파일 접근만 허용한다.

## 6. 실행과 협업 규칙

첫 버전은 한 번에 한 작업만 실행한다. 두 에이전트는 같은 작업 worktree를 **순서대로** 사용한다. 검토자는 읽기와 검증 작업을 수행하고 소스 수정은 구현자가 담당한다. 따라서 초기 버전에 병렬 수정·자동 충돌 해결은 필요하지 않다.

협업 단계는 `구현 → 검토 → 수정 → 재검토`이다. 최초 검토 이후 수정은 최대 2회로 제한한다. 이후에도 문제가 남으면 '사용자 확인 필요' 상태로 종료하고 미해결 사항을 보여준다. 검토자가 확인하지 못한 항목을 완료로 취급하지 않는다.

인계 데이터에는 최초 요청, 단계 목표, 기준 커밋, 작업 폴더, 변경 파일, 구현 결과, 실행한 검증과 결과, 검토 지적 사항을 포함한다. 두 공급자의 비공개 내부 컨텍스트가 공유된다고 가정하지 않는다. 검토 출력은 합의된 구조로 검증하며 파싱 실패 시 명시적으로 오류를 표시하고 다음 단계로 진행하지 않는다.

실행 상태는 `queued / running / waiting_approval / waiting_input / completed / failed / cancelled / interrupted / needs_attention`으로 구분한다. 에이전트의 `reading / editing / executing / reviewing` 활동은 별도 필드로 관리한다.

각 이벤트에는 `eventId`, `sequence`, `runId`, `agentId`, `timestamp`, `type`, `payload`를 포함한다. 재연결 시 마지막으로 받은 sequence 이후의 이벤트를 재생하고 중복은 eventId로 제거한다. 원본 공급자 이벤트는 진단용으로 보존하되 UI 상태는 정규화된 이벤트를 사용한다.

## 7. 오류와 복구

- CLI·SDK 연결 또는 인증 실패: 실제 오류를 보여주고 실행을 시작하지 않는다. 가짜 진행 상태로 대체하지 않는다.
- 승인 요청: 해당 작업과 명령·파일 변경 정보를 표시한다. 거절을 성공으로 처리하지 않는다.
- 중단: 활성 에이전트의 취소 기능을 호출하고 종료 확인 후 cancelled로 전환한다. 취소 중에는 후속 에이전트를 실행하지 않는다.
- 브라우저 새로고침: 서버 작업은 계속되며 저장된 상태와 이벤트로 화면을 복구한다.
- 로컬 서버 재시작: 이전 실행을 자동으로 재실행하지 않는다. 진행 중이던 작업은 interrupted로 기록하며 잔존 프로세스 여부와 작업 폴더를 확인할 수 있게 한다.
- 실행 실패: 로그·부분 결과·변경 파일을 보존한다. 실패 후 재시작은 명시적 사용자 동작으로만 수행한다.
- worktree 정리: 결과에 접근할 수 있도록 유지하며, 변경이 남은 폴더는 자동 삭제하지 않는다.

## 8. 검증과 인수 기준

1. **상태 변환 검증:** 두 공급자의 실제 형식을 따른 이벤트 fixture로 도구 시작·종료, 승인 대기, 실패, 취소, 중복 이벤트를 검증한다.
2. **협업 검증:** 구현 결과가 검토자에게 전달되고, 검토 지적이 구현자에게 전달되며, 최대 수정 횟수와 실패 시 후속 실행 차단이 동작한다.
3. **격리 검증:** 원본 프로젝트와 커밋되지 않은 변경을 건드리지 않고 전용 worktree에서만 소스가 변경된다.
4. **브라우저 검증:** 프로젝트 선택, 작업 입력, 캐릭터 선택, 로그·diff 표시, 승인·거절, 중단, 새로고침 복구를 확인한다.
5. **실제 연결 검증:** 인증된 두 공급자로 작은 샘플 Git 프로젝트의 파일 수정과 검토를 실행한다. 연결 검증이 불가능한 경우 그 공급자를 검증 완료로 표시하지 않는다.
6. **시각 상태 일치:** UI의 에이전트 수·실행 상태·협업 단계가 서버 상태와 일치하고, 완료·실패·응답 대기가 애니메이션과 텍스트 양쪽에 반영된다.
7. **페르소나 적용:** 공급자·모델·직급·업무가 독립적으로 저장되고, 선택한 직급 지침이 실제 실행 입력에 포함된다. 역할 반전과 신입 선택에서도 권한 정책은 바뀌지 않으며 실행 기록에 당시 모델·직급이 남는다.

실제 에이전트 연결과 화면 개발은 분리한다. 개발용 이벤트 재생 기능에는 항상 '데모'를 표시한다. 실제 연결·협업 검증 전에는 제품 전체가 완성되었다고 보고하지 않는다.

## 10. 설계 검토 기록

- 사용자 요청과 일치: 로컬에서 직접 작업 지시, 에이전트별 상태 확인, Claude·Codex 협업을 포함한다.
- 범위 제한: 두 에이전트·한 프로젝트·순차 협업으로 첫 실행 가능한 제품에 집중한다.
- 상태 일관성: 관측 가능한 이벤트와 시각적 활동을 구분하고 실패·대기·중단을 명시한다.
- 확인되지 않은 연동: 인증 재사용과 실제 공급자 실행은 가정하지 않고 인수 검증에 포함한다.
- 설계 내 미결 자리표시자 및 상충된 실행 방식 없음.
