# Slack으로 일 맡기기 + 코디네이터 — 설계

## 목적

지금은 폴더마다 터미널을 열어 Claude/Codex를 띄우고, 회의록·계획·코딩·문서·Confluence 게시·Jira 티켓을
사람이 이어 붙인다. 일 하나하나보다 **이음새(맥락을 들고 다음 폴더로 가서 다시 설명하는 일)** 가 번거롭다.

이 프로젝트는 그 이음새를 줄이는 첫 단계다. Slack에서 한 줄로 일을 맡기면 오피스의 코디네이터가
맞는 동료(폴더 + 하네스 + 역할)에게 나눠 주고, 진행·질문·승인·결과가 그 Slack 스레드 하나로 돌아온다.
구조는 OpenClaw(에이전트 = 작업 폴더 + 역할 문서, 바인딩 라우팅, 스레드 = 세션, chief-of-staff 코디네이터)를 따른다.

전체 그림에서 이 문서는 1번이다. 나머지는 별도 프로젝트로 이어진다.

1. **Slack 입구 + 코디네이터 (이 문서)**
2. 여러 동료가 일하는 오피스 화면, 추가 투입 시각화
3. 회의록 → 계획 → 작업 사슬 (`meeting-minutes` 연동, Notion/Jira/Confluence 흐름)
4. 하네스(pstack 등) 등록 개선 — 이 문서의 "동료" 정의가 그 기반이 된다

## 목표 / 비목표 / 실패 조건

**목표**
- Slack DM 또는 바인딩된 채널에 쓴 한 줄이 오피스 작업이 되고, 결과가 같은 스레드로 온다.
- 코디네이터가 동료를 골라 배정하고, 필요하면 여러 동료에게 나눠 맡긴다.
- 에이전트의 질문·승인 요청을 Slack 버튼/답글로 처리한다.
- 같은 스레드에 쓴 답글은 그 일의 후속 지시가 된다.
- 동료를 쉽게 정의한다: 폴더, 하네스(등록된 명령 — `claude`, `codex`, pstack 같은 래퍼), 역할, 바인딩.

**비목표**
- Jira·Confluence·Notion API를 오피스가 직접 구현하지 않는다. 동료의 하네스에 붙은 MCP를 에이전트가 쓴다.
  (현재 Claude에는 Slack/Gmail/Drive만 연결돼 있고 Atlassian·Notion은 없다. 사용자가 MCP를 연결하는 건 이 프로젝트 밖의 준비 작업이다.)
- 오피스 평면도 개편 (2번 프로젝트).
- 다른 사람이 봇에게 일을 맡기는 것. **이 봇은 사용자 한 명 전용이다.**
- 맥이 잠들어 있을 때의 처리. 지금처럼 맥이 켜져 있을 때만 동작한다.

**실패 조건 (동작해도 안 쓰게 되는 경우)**
- **너무 자주 묻는다.** 코디네이터는 애매해도 가장 그럴듯한 배정으로 착수하고, 그 가정을 첫 답글에 적는다.
  질문은 (a) 맞는 동료가 아예 없을 때, (b) 승인 정책상 확인이 필요한 행동일 때만 한다.
- **느리다.** 메시지를 받으면 3초 안에 👀 리액션, 10초 안에 배정 계획 답글이 와야 한다.
- **허락 없이 밖에 올린다.** 외부 쓰기는 기본이 "확인"이다. 다만 사용자가 행선지별로 "자동"으로 바꿀 수 있어야 한다
  (사용자: "조심스럽긴 한데 될 때도 있다").

## 개념

### 동료 (Coworker)

OpenClaw의 agent에 해당한다. 하나의 동료는 다음으로 정의된다.

| 필드 | 설명 |
|---|---|
| `id`, `name` | 슬러그와 표시 이름 (`skt-dev`, "SKT 개발") |
| `folder` | 작업 폴더(기본 cwd). git 저장소가 아니어도 된다 (문서 폴더 등) |
| `harness` | engine(`claude`/`codex`) + 실행 명령 + **플러그인·스킬 묶음** + 모델(선택). 아래 "하네스" 참고 |
| `role` | 역할 설명 한 단락. 코디네이터가 배정 판단에 쓰고, 동료 프롬프트 앞에 붙는다 |
| `mode` | 작업 방식. `solo`(구현만, 문서·컨텐츠용) 또는 `collaborate`(구현 → 리뷰 → 수정, 코드용). 기존 `Mode`에 대응. collaborate의 리뷰는 지금처럼 **반대 엔진의 기본 실행**이 맡는다 *(설계자 판단 — 기존 동작 유지)* |
| `bindings` | 이 동료로 바로 가는 Slack 채널 id 목록 (선택) |
| `approvals` | 도구 이름 패턴별 `auto`/`ask` 규칙 (아래 승인 정책) |
| `createdBy` | `user` 또는 `coordinator`(사용자 승인 후 생성). OpenClaw provenance와 같은 의미 |

- 기존 프로젝트·하네스 설정(`RepoHarness`, `launch-harnesses`)은 동료 정의가 참조한다. 새로 중복 저장하지 않는다.

### 하네스

동료의 하네스는 두 층이다.

1. **실행 명령.** 배정 Run의 어댑터가 실행할 CLI다. 지금 Claude 어댑터는 `pathToClaudeCodeExecutable: 'sy'`,
   Codex 어댑터는 `syc app-server --stdio`로 하드코딩돼 있다. 이 자리에 동료의 명령을 넣는다(기본값은 지금 값 그대로).
   Codex 래퍼는 `app-server --stdio`를 지원해야 하고, 동료 저장 시 이를 확인한다.
2. **플러그인·스킬 묶음.** pstack은 이 형태다(사용자 확인: 별도 명령이 아니라 설치되는 묶음). 기존 `HarnessChoice`
   (`plugins`, `skills`, `projectDoc`)와 `prepareClaudeHarness`/`codexHarnessConfig`가 이미 저장소별로 이걸 한다.
   동료는 이 선택을 자기 것으로 가진다. pstack 같은 묶음을 쉽게 고르는 화면 개선은 4번 프로젝트지만,
   동료 설정에서 기존 카탈로그(`/api/harness/catalog`) 중 묶음을 고를 수 있는 것까지는 이 프로젝트에 포함한다.
- 저장 위치는 오피스 데이터 디렉터리(레포 밖). 화면의 **동료 설정**에서 추가·수정·삭제한다.
- 처음 실행 시 동료가 없으면, 최근 작업한 프로젝트 목록에서 동료 후보를 제안하는 화면을 보여 준다(빈 명단으로 시작하지 않게).

### 코디네이터

- 동료 명단 맨 위에 고정된 특별한 동료. 삭제할 수 없다.
- 오피스 데이터 디렉터리 안의 전용 폴더(`coordinator/`)에서 돈다. 그 폴더의 `AGENTS.md`에 운영 규칙이 있고, 사용자가 수정할 수 있다.
- 구현: 이미 쓰는 `@anthropic-ai/claude-agent-sdk`의 `query()`에 **오피스 서버가 in-process MCP 도구**를 제공한다.
  코디네이터는 터미널을 직접 열거나 파일을 고치지 않는다. 모든 배정이 오피스 서버를 거쳐 기록된다.
- 모델: 속도 우선. 배정은 빠른 모델로 한다 (빌더가 실측해 정한다. 10초 목표를 못 맞추면 그게 기준이다).

코디네이터 도구:

| 도구 | 하는 일 |
|---|---|
| `list_coworkers` | 명단(id, name, role, folder, mode, 현재 바쁜지) |
| `delegate(coworkerId, task, after?)` | 동료에게 일을 맡겨 Run을 만든다. `after`는 먼저 끝나야 하는 다른 배정 id. 앞 배정의 결과 요약이 뒤 배정의 맥락으로 들어간다 |
| `follow_up(assignmentId, prompt)` | 배정에 후속 지시 (기존 `parentRunId` 후속 실행). 배정이 아직 진행 중이면 끝난 직후 이어서 실행되도록 대기시키고, 상태 메시지에 "후속 지시 대기"로 보인다 *(설계자 판단)* |
| `cancel(assignmentId)` | 사용자가 "멈춰"처럼 명시적으로 말했을 때만 진행 중 배정을 중단 |
| `job_status` | 이 일의 배정별 상태·요약 |
| `propose_coworker(name, folder, role, harness)` | 새 동료 제안. 스레드에 승인 버튼이 뜨고, 승인돼야 생성된다 |
| `reply(text)` | 스레드에 코디네이터 이름으로 답글 |

코디네이터는 다음 시점에만 깨어난다: 새 일, 스레드 답글, 배정 하나가 끝났을 때(다음 배정 판단 + 최종 보고).
작업 중 계속 붙어 있지 않는다.

### 일 (Job)

- **Slack 스레드 하나 = 일 하나.** 키는 `team:channel:thread_ts`.
- 일은 배정(Assignment) 여러 개를 가진다. 배정 하나 = 기존 Run 하나(동료의 폴더·하네스·모드로 실행).
- 오피스 화면에서 시작한 Run은 지금처럼 동작한다. Slack에서 온 일이라는 표시(출처 배지와 스레드 링크)만 추가된다.

## 흐름

```
사용자 DM: "어제 skt 회의록 보고 이번 주 계획 세워서 Confluence 초안 만들어줘"
  → (≤3s) 👀 리액션
  → 코디네이터 실행 (list_coworkers → delegate ×2)
  → (≤10s) 스레드 답글: "회의록 동료 → 기획 동료 순서로 진행할게요.
                         회의록은 meeting-minutes/out 의 가장 최근 것으로 가정했어요."
  → 배정 1 실행 … 진행 상황은 '상태 메시지' 하나를 계속 수정해서 표시
  → 배정 2 실행 … Confluence 게시 도구 호출 → 승인 정책 'ask' → 스레드에 [승인][거절] 버튼
  → 사용자가 Slack에서 [승인]
  → 배정 끝 → 코디네이터 깨어나 최종 보고: 요약 + 산출물(PR 링크, Confluence 링크, 문서 파일 첨부)
사용자 스레드 답글: "일정 하루 당겨서 다시"
  → 코디네이터가 follow_up(배정 2) 결정 → 이어서 실행
```

바인딩된 채널(`#office-skt` → `skt-dev`)에 쓴 메시지는 코디네이터를 건너뛰고 그 동료에게 바로 배정된다.
결과 보고 형식은 같다. 그 스레드에서 다른 동료가 필요하다고 사용자가 쓰면 그때 코디네이터가 개입한다.

## Slack 연동

- **Socket Mode** 봇. 공개 URL·서버 불필요. 오피스 서버 프로세스 안에서 연결을 유지하고, 끊기면 재연결한다.
- **소유자 전용.** 설정에 등록한 Slack user id 하나에서 온 메시지만 처리한다. 다른 사람, 봇, 자기 자신이 보낸 메시지는 무시한다.
  버튼 응답도 같은 user id인지 확인한다. 이 봇은 사용자 권한으로 로컬에서 코드를 실행하므로 이 검사가 핵심 보안 경계다.
- 채널에서는 봇을 멘션했거나 바인딩된 채널일 때만 반응한다. DM은 항상 반응한다.
- **토큰** (bot token, app token)은 설정 화면에서 입력받아 오피스 데이터 디렉터리의 권한 0600 파일(또는 macOS Keychain)에 둔다.
  레포·로그·이벤트 payload에 남기지 않는다. 상주 서비스(launchd)는 셸 환경 변수를 복사하지 않으므로 환경 변수만으로는 부족하다.
- 스레드 도배 방지: 일마다 **상태 메시지 하나**를 두고 수정(`chat.update`)으로 진행을 보여 준다. 새 답글은
  배정 계획, 질문/승인, 최종 보고, 실패일 때만 단다.
- 질문(`AskUserQuestion` 등): 선택지는 버튼, 자유 입력은 스레드 답글로 받는다. 기존 Interaction 응답 API를 그대로 호출한다.
- 산출물: PR·외부 링크는 본문에, 작업이 만든 문서(기존 task-documents가 찾는 파일)는 일정 크기 이하면 Slack 파일로 첨부한다.
- 오피스 화면에서 같은 질문에 먼저 답하면 Slack 버튼은 "오피스에서 처리됨"으로 바뀐다. 반대도 같다.

## 승인 정책

지금은 전역 `manual`/`auto` 하나다. 이를 **동료별·도구 패턴별 규칙**으로 확장한다.

- 규칙: `{ pattern: "mcp__atlassian__*create*", action: "ask" | "auto" }` 목록. 위에서부터 첫 일치가 적용된다.
- **동료 규칙이 전역 설정보다 우선한다.** 전역이 `auto`여도 동료 규칙이 `ask`면 묻는다. Claude는 전역 `auto`일 때
  `bypassPermissions`로 돌아 `canUseTool`이 호출되지 않으므로, 규칙은 SDK의 PreToolUse hook에서 강제한다 *(설계자 판단)*.
- 규칙은 동료의 폴더에서 도는 **모든 Run**에 적용된다(Slack에서 왔든 오피스 화면에서 시작했든). 입구에 따라 같은 폴더의
  외부 게시가 자동이 되기도 하고 확인을 받기도 하면 안 되기 때문이다 *(설계자 판단)*. 터미널 모드(사용자가 직접 띄운 CLI)는 대상이 아니다.
- 기본값: 동료 폴더 안의 읽기·편집·명령은 기존 전역 설정을 따르고, **외부 MCP의 쓰기 성격 도구는 `ask`**.
  "쓰기 성격"의 판정은 빌더가 정하되, 모르면 `ask` 쪽으로 기운다.
- **Codex:** app-server가 MCP 도구 호출마다 승인 요청을 올리는지 구현 첫 단계에서 실측한다. 강제할 수 없으면
  Codex 동료는 **외부 MCP 쓰기 도구 없이** 실행하고, 동료 설정에 그 이유를 표시한다. 외부 게시는 Claude 동료가 맡는다(사용자 결정).
- 권한 확장 요청(`isToolApproval`이 false인 것)은 지금처럼 항상 사람에게 묻는다.
- 자동 처리된 승인도 스레드 상태 메시지에 한 줄로 남긴다 ("Confluence 초안 생성 — 자동 승인").
- 설정 화면에서 동료별로 고른다. 자주 쓰는 행선지(Confluence 게시, Jira 발급, Notion 페이지, PR, Slack 다른 채널 발송)는 미리 만든 토글로 보여 준다.

## 동시 실행

지금 오케스트레이터는 전역 `busy`로 한 번에 Run 하나만 돈다. 코디네이터가 여러 동료에게 나눠 주면
줄이 길어져 "느리다"는 실패 조건에 걸린다.

- **동료 단위 직렬, 동료 간 병렬**로 바꾼다. 같은 동료(같은 폴더)의 Run은 순서대로, 다른 동료는 동시에.
- 전역 동시 실행 상한(기본 3, 설정 가능)을 둔다. 초과분은 대기하고 상태 메시지에 "대기 중 · 앞에 N개"로 보인다.
- *(설계자 판단 — 사용자와 합의한 항목 아님.)* 오케스트레이터 변경이 크면 이 부분만 먼저 별도 커밋으로 낸다.

## 화면 (최소)

- **동료 설정**: 명단, 추가/수정(폴더 선택, 하네스·모델, 역할, 모드, 바인딩 채널, 승인 규칙), 코디네이터 `AGENTS.md` 열기.
- **Slack 연결 설정**: 토큰 입력, 소유자 user id(연결 테스트 시 자동 확인), 연결 상태.
- 작업 목록에 Slack 출처 배지와 스레드 열기 링크.
- 오피스 평면도 개편은 하지 않는다.

## 사용자가 정한 것

- 첫 단계는 "Slack으로 일 맡기고 결과 받기".
- Slack은 알림 전용이 아니라 일을 맡기는 입구 (OpenClaw처럼).
- OpenClaw 구조를 따른다. 코디네이터를 첫 단계에 포함한다.
- 외부 게시는 조심하되, 자동으로 해도 되는 경우가 있다.
- 자주 묻거나 느리면 안 쓴다.
- pstack은 플러그인·스킬 묶음이다.
- Codex에 외부 게시 확인을 강제할 수 없으면 Codex 동료에서 외부 쓰기 도구를 끈다.

## 빌더에게 맡기는 것

- 동료·일·배정의 저장 스키마와 마이그레이션 (기존 `store.ts` 방식을 따른다).
- Slack 클라이언트 라이브러리 선택 (`@slack/bolt` 또는 `@slack/socket-mode` + `@slack/web-api`). 패키지 관리자는 이 레포가 쓰는 npm.
- 코디네이터 모델, 프롬프트 세부, `AGENTS.md` 초안.
- 상태 메시지 문구와 Block Kit 레이아웃.
- 테스트 전략. 최소한 다음은 자동 테스트로 증명한다: 소유자 외 메시지 무시, 스레드 → 일 매핑, 승인 버튼 → Interaction 응답, 동료 간 병렬/동료 내 직렬, 토큰이 로그·이벤트에 남지 않음.
